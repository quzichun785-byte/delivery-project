# 轻量决策到工程派单示例

本例展示母子结构如何减轻调研负担，同时不降低工程要求。示例只说明工作流，不生成真实业务系统。

## 场景：增加固定车辆模拟通行

### 第一步：母骨架完成轻量调研

在母窗口执行：

```text
/start-product
```

形成一张轻量卡：

- 问题：是否先做固定车辆，而非完整访客系统？
- 证据：当前只需要验证车辆权限、开闸和进出记录；
- 方案 A：先做固定车辆闭环，异常场景保留；
- 方案 B：同时开发访客、收费和复杂报表，范围过大；
- 决策：采用方案 A，访客只保留为后续候选。

执行：

```text
/decide-task 01
```

轻量卡即可结束，不需要任何工程测试证据。

### 第二步：需要实现时再派工程卡

```text
/dispatch-task 02
```

母骨架在子工程卡 A 区写入：

- 目标：固定车辆识别后按权限模拟开闸；
- 范围：车辆档案、权限判断、开闸事件、进出记录、异常告警；
- 不做项：真实厂商接入、停车收费、复杂访客流程；
- 验收：允许、禁止、权限过期、重复事件和设备离线场景。

### 第三步：子骨架按工程标准实现

```text
/bootstrap-engineering
/start-task 02
/build-task 02
/verify-task 02
/review-task 02
/accept-task 02
```

子骨架需要证明：

- 固定车允许，禁止车拒绝；
- 权限过期不能开闸；
- 重复事件不会重复开闸；
- 设备离线有异常和人工处理路径；
- 识别、开闸指令和回执可分别追踪；
- 功能测试和至少一个集成场景真实通过；
- HIGH 风险任务完成独立审查。

### 第四步：母子分别验收

子签工程证据，母签产品场景。只有双方均为 `APPROVED`，才能由母或母子确认 `DONE`。

## 这个示例体现了什么

- 调研时可以轻量决策，不必为了形式做工程验证；
- 开发时不能因为需求看起来简单就跳过工程闸口；
- 母负责控制产品范围，子负责证明实现质量；
- 母子双签不是形式主义，而是分别防止“做错产品”和“把产品做错”。
