# 企业级工程交付主纲（delivery-charter）

> 本主纲是 `delivery-project` 的首要决策基线。**主角是企业级可交付代码，母子骨架只是实现手段。**任何模板、命令、校验或母子协作调整，都不得削弱以下工程决策。

## 1. 目的与边界

### E01 主目的：企业级可交付，而非一回合演示
- 目标不是“页面能开、功能看似完整”，而是代码能够被测试、集成、部署、回滚、运维和交接。
- 母子骨架、双目录和派单都不是目的；只有能提高交付质量或减少不必要流程负担的机制才保留。

### E02 母子结构的从属作用
- 母骨架只负责轻量调研、分析、决策、工程派单和产品结果确认，避免非代码任务被迫走重型工程流程。
- 小决策可直接写 INBOX/DECISIONS，不必事事建卡；需要写代码时才进入子骨架的重型工程流程。
- 母子双签只用于工程交付，不给普通调研决策增加测试、集成、回滚等无关要求。

### E03 工程质量与业务确认是两条线
- 模拟数据不降低工程质量；工程测试通过也不代表现场业务、设备、合同或验收条件已确认。
- DONE 只代表当前工程任务完成，不等于生产发布。

## 2. 开发方式

### E04 垂直切片，禁止一次性造整系统
- 以可独立验证的小业务闭环为单位，不以“全数据库→全后端→全前端→最后测试”分层大开发。
- 切片不是必须小到一个函数，也不能大到整个模块；应能在一个窗口内完成实现和验证。

### E05 每片完成即集成
- 每实现一个可运行增量就运行相关集成流程，不等所有轮子造完再拼整车。
- 范围外问题记 INBOX，不顺手扩改；同一任务同一时间只开一个执行窗口。

### E06 命令必须分阶段，不能重新变成长任务
- 技术评审、实现、验证、独立审查和工程验收分别使用 `/start-task`、`/build-task`、`/verify-task`、`/review-task`、`/accept-task`。
- 命令数量不是目的，关键是每个命令边界清晰、出口明确，不允许一个命令承担整个开发过程。

## 3. 任务与工程基线

### E07 先验收设计，再写实现
- 每张工程卡必须自足：背景、精确输入、范围、不做项、接口/数据契约、验收矩阵、风险预案和日志。
- 正常、异常、权限、幂等、并发、审计、精度、迁移、回滚等质量项必须标适用或 N/A+理由，禁止无声删除。

### E08 工程基线先于业务切片
- 首个业务切片前执行 `/bootstrap-engineering`，按真实开发仓建立依赖锁定、配置/密钥、启动停止、健康检查、初始化/迁移/回滚、错误与日志、lint/typecheck、测试与数据种子、CI、模拟/真实适配、备份恢复和可观测性。
- 已有可用配置不得为套模板而替换；未知技术栈先探测，不编造；基线未通过则业务切片 BLOCKED。

### E09 不预置技术栈和 CI 模板
- 根据真实代码仓、锁文件、既有测试和 CI 建立基线，不生成看似完整但不可运行的通用模板。

## 4. 状态与变更

### E10 主状态与必要辅助状态
- 主交付链：DRAFT → DISPATCHED → READY → BUILD → VERIFY → REVIEW → ACCEPT → DONE。
- BLOCKED 用于技术/资料阻塞，BLOCKED_PRODUCT 用于产品矛盾、不可实现或范围变更。
- D 区必须追加 `日期 | 角色 | status: 源 -> 目标 | task_version=版本`，当前状态必须与最后转移一致；不能只改 frontmatter。
- 非法跳级、缺历史、最终状态不符、返工路径不合法均应被机械拦截。

### E11 产品变更必须回退而非缩小需求
- 子发现产品问题时不得改 A 区，必须 BLOCKED_PRODUCT 退回；母修订并提升 task_version 后重新 DISPATCHED。
- 阻塞恢复必须校验 blocked_from 与历史；产品重新派单必须由母执行，最终 DONE 必须由母或母子确认。

## 5. 测试与可复现证据

### E12 真实测试，禁止自我宣布通过
- 先跑既有测试，再跑新增测试；正常、异常、权限和集成路径必须按任务风险覆盖。
- 未执行写 NOT_RUN，不得以截图、编译成功、单次点击或 Agent 总结写成 PASS。
- 测试必须真正断言业务结果，不能只追求函数不报错或覆盖率数字。

### E13 可复现证据包
- 至少记录依赖版本、环境、模拟数据/随机种子、数据库初始化与迁移、实际命令、预期结果、通过/失败数量和原始输出位置。
- 原始大日志放 artifacts/ 或 CI，登记留存策略；任务卡只留摘要和路径。
- 新窗口或另一个 Agent 应能按文档重新执行并得到相同结果。

### E14 每片功能测试与集成验证不可合并跳过
- VERIFY 同时包含功能测试和至少一个相关集成场景，两者都有独立证据，不得以“已合并”名义省略任一项。

## 6. 风险、成熟度与独立审查

### E15 风险决定审查强度，默认从高
- LOW/MEDIUM 可按风险轻量处理；HIGH/CRITICAL 必须由干净上下文独立 Agent 审查任务卡、实际 diff 和原始测试证据。
- 风险默认 HIGH；降级必须在 D 区写理由和批准人，计费、权限、设备控制、迁移、生产发布不得由执行 Agent 自行降级。
- 审查只查不改；主执行者复核合理项并复测。无发现也允许，不制造问题凑数。

### E16 成熟度决定证据深度，不与风险混淆
- `target_maturity` 必填：DEMO 要 C3/C4；PILOT 另要 C6 异常/权限/部署/回滚或合理 N/A；PRODUCTION 另要 C7 生产就绪证据且不能 N/A。
- C7 包括安全、性能/容量、备份恢复、健康检查、指标/告警、迁移和发布验证。
- 不能用演示级证据宣称正式交付级，也不能用工程成熟度替代业务验收。

### E17 关键生产事项需要人工专业评审
- CRITICAL 任务 DONE 前，除独立 Agent 审查外，还需按任务要求完成人工专业评审并留存人员、日期和证据。

## 7. 验收与生产运维

### E18 母子双签必须完整，不接受空双签
- 子签工程：实现、测试、独立审查、集成与回滚满足要求；母签产品：范围、业务规则和产品验收场景满足要求。
- DONE 时元数据与 E1/E2 结论必须一致，验收证据路径、人员、日期、遗留问题完整且证据文件存在。
- 子只能签 E2，不能单独改 DONE；最终确认由母或母子执行。

### E19 生产运维必须具体
- 正式交付需检查健康检查、结构化日志、指标/告警、必要链路追踪、权限与敏感信息、依赖漏洞、性能容量、备份恢复、发布回滚和运维交接。
- 不能只写“监控、安全、性能”概括，必须有实测或明确未决项。

### E20 多仓与仓外资产必须登记
- 开发仓、模拟器、部署配置、旧代码、交付物及验证证据目录登记 `docs/ASSETS.md`，独立 Git 仓记录指针 commit。
- 资产不得只存在于某个窗口的记忆中。

## 8. 校验与演进纪律

### E21 基础机械校验必须存在，但不夸大能力
- 校验目录、协议、任务卡完整性、状态转移、角色、成熟度、证据路径、双签和人工评审。
- 机械校验只能证明结构与证据存在，不能证明测试有业务价值、代码架构合理、审查意见正确或验收人有权限。

### E22 文档是多窗口资产，但不得形式主义
- STATUS 管当前状态，DECISIONS 管决策，任务卡管单任务，开发交接手册管实现/运行/坑位，TESTING 管当前实测，OPERATIONS 管生产运维。
- 文档必须帮助复现和接手，不能用“全部打勾”替代真实工程结果。

### E23 不擅自执行外部动作
- 不自动提交、推送、合并、部署或正式发布；这些动作必须另行明确授权。
- 公开发布、涨星或交付形式都不是主目的，技能本身好用和能提升交付质量才是目的。

### E24 技能自身必须小步验证，不夸大结论
- 先用一个普通切片验证可用性，再用一个高风险切片验证异常、权限、幂等、离线和独立审查。
- 试验只能证明工作流可用，不能直接证明它能自动产出生产级代码；仍需真实项目检验和持续修正。
